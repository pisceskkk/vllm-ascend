vLLM Ascend PCP/DCP 独立于非 CP 路径的代码分析报告

本报告梳理 vLLM Ascend 中 PCP（Prefill Context Parallel）与 DCP（Decode Context Parallel）相对普通非 CP 路径产生独立逻辑的代码，并按“触发特性—差异原因—代码落点—风险/验证点”归类。

1. 总体结论

  • CP 共性 独立路径的根因是 KV cache 从“每 TP rank 一份完整序列”变为按序列维度在 pcp_size * dcp_size 上分片，导致 block table、slot mapping、attention metadata、KV 传输和图捕获都必须理解 CP rank/interleave。
  • PCP 主要服务长序列 prefill 降 TTFT：需要对 query 做 head-tail 切分、padding、all-gather restore、非均匀 chunk 还原，因此在 model runner 和 attention prefill 路径引入大量独立元数据。
  • DCP 主要服务 decode 阶段 KV cache 去冗余：复用 TP 通信域，但 Q heads 在 DCP 组内不同，attention 结果需要跨 DCP 交换 output/LSE 并做在线 softmax 合并。
  • PCP 与 DCP 同时启用时，差异不是简单叠加：PCP 负责序列切分/还原，DCP 负责 head 维与 KV 分片通信，最终通过统一的 CP attention update、CP slot mapping 和 CP block table 组合起来。

3. 关键差异机制

3.1 KV cache 分片与 slot mapping

普通路径中 position 可直接定位到本地 block 的 slot；CP 路径先把 block 扩展为虚拟 block，按 cp_kv_cache_interleave_size 在 cp_size 个 rank 间交错。实现上，slot kernel 对每个 token 计算 block_offsets // CP_INTERLEAVE % CP_SIZE == cp_rank，只有本 rank token 才写本地 slot，否则写 PAD。这是所有 CP 差异的底层基础。

3.2 PCP：prefill query 切分、padding 和顺序恢复

PCP 为了让长 prefill 在多卡上均衡，把序列切成 2*pcp_size 份后首尾配对。这样会改变 token 顺序，并可能引入 padding。独立的 PCPManager 因此维护 restore index、scatter index、unpad mask、sample slot mapping、query lens full buffer 和混合 attention 标记。非 CP 路径没有这些元数据，因为非 CP token 顺序就是调度顺序。

3.3 DCP：decode KV 去冗余与 output/LSE 合并

DCP 复用 TP 域。由于 DCP group 内 Q head 分布不同而 KV cache 又按序列切分，本地 attention 只能得到局部上下文上的 output/LSE。CP common 路径先把 output 与 LSE 拼接，DCP 用 all-to-all 交换，PCP 再按需 all-gather，最终用 NPU attention update 按 LSE 执行在线 softmax 合并。

3.4 Chunked prefill 与 Prefix Cache

当开启 chunked prefill 或 APC 时，一个请求可同时包含 decode token、已缓存 context 和本轮 prefill query。CP 路径必须知道每个 PCP/DCP rank 上的 local context length，并为 chunked request 构造过滤 mask、local starts、KV recover index；否则局部 KV 与 query 的因果 mask 会错位。

3.5 Speculative decoding

Spec decode 把 decode query 从 1 个 token 扩展为多个草稿 token，放大了 CP slot mapping 与 block table 的一致性要求。Ascend 为 DCP 校验 draft TP/DCP 的 head 可整除关系，并在 proposer 中为 CP 分配更长的 slot mapping buffer、复制 block table、传递 long sequence metadata。

3.6 PD/KV transfer 与 block interleave 约束

KV transfer、KV pool、Mooncake 等场景需要跨进程/跨节点搬运 KV。若 CP 使用 token interleave，远端需要按 token 粒度重组 KV，复杂且低效；因此平台校验要求 CP 场景中 cp_kv_cache_interleave_size 与 block_size 相等，SFA 也会自动覆盖为 block interleave。

4. 代码级风险点与建议

  • CPU/NPU 同步： CP metadata builder 中仍有 .item() 与 CPU fallback；热路径应优先依赖 CPU mirror，避免 AsyncScheduler 被 D2H 同步阻塞。
  • 索引一致性： PCP 的 restore/scatter/unpad、chunk recover index、spec decode slot mapping 必须随 query layout 同步更新，新增 feature 时应先确认 token 顺序是否被 PCP 改写。
  • 通信域组合： PCP、DCP、TP、PP、DP、EP、P/D disaggregation 共同出现时，group rank layout 是正确性的第一前提，相关变更必须覆盖多维组合测试。
  • 后端一致性： FA、MLA、SFA、GDN/FLA 等后端各自有 CP 专用分支；新增 attention backend 不应只复用非 CP builder，应显式实现或声明不支持 CP。
  • 图捕获资源： CP 引入 collective 和额外 workspace，ACL Graph capture sizes 需要保守预算；spec decode + PCP/DCP + full/piecewise graph 是高风险组合。

结论：PCP/DCP 不是单一 attention 优化，而是一组围绕“序列维分片 KV cache”和“长序列/解码通信合并”的端到端路径。新增或修改与 token layout、KV 写入、attention metadata、采样、KV 传输、图捕获相关的功能时，都需要显式审视 CP 路径。
